# gyrfalcon — навигация по 1С через индекс

Индекс отвечает за миллисекунды и отдаёт **адреса и выжимки**, а не файлы.
Прямой поиск (`grep`, `Glob`, `Select-String`) по выгрузке конфигурации 1С
даёт мусор и стоит десятки тысяч токенов: XML-выгрузка огромна, связи модели
в тексте не видны.

Замер 28.08.2026 на Бухгалтерии 3.0.190.11 (18 230 модулей): типичный вызов —
**1 219 знаков** выдачи.

## Матрица: вопрос → вызов

| Вопрос | Вызов |
|---|---|
| Есть ли такой объект / метод / модуль? | `find(query, kind)` |
| Не знаю имени, знаю смысл | `find(query="как считается себестоимость", semantic=true)` |
| Какие реквизиты, типы, табличные части? | `object(name)` |
| **Нужно написать код по задаче** | `assist_bsl(task, module, source)` — методы, объекты, официальный синтаксис и дополнения |
| **Как работать в типовой конфигурации** | `kb_1c(project, query)` — пользовательская встроенная справка только выбранного проекта; её версию и адрес называйте в выводе |
| **Какие принятые практики и исключения есть у проекта** | `project_practices(project)` — общий нормализованный слой и принятые локальные правила; не путайте их с кандидатами |
| **Что требует общий стандарт 1С по теме** | `standards_1c(project, query)` — поиск по единому справочнику v8std; проектные исключения сверяйте через `project_practices` |
| По каким регистрам двигает документ? | `object(name, parts=["movements"])` или `movements(document)` |
| Кто пишет в этот регистр? | `movements(register)` |
| Кто вызывает процедуру? | `callers(method, direction="in")` |
| Что вызывает эта процедура? | `callers(method, direction="out")` |
| Индекс конфигурации больше не нужен | `delete_project(project)` — удаляет ИНДЕКС, не исходники |
| **Какие конфигурации знает сервер? Что писать в `project`?** | `list_projects()` |
| Влияние правки (транзитивно) | `callers(method, direction="in", depth=3)` |
| **Что затронет планируемая правка до diff?** | `impact(symbol, kind)` — граф вызовов, подписки, задания и адресные метаданные |
| **Что сломает этот MR / мои правки?** | `detect_changes()` — diff → задетые методы → риск |
| Влияние правки против ветки | `detect_changes(base_branch="main", depth=3)` |
| Показать тело процедуры | `read(method, module)` |
| Ищу текст, которого нет в именах: GUID, сообщение, кусок запроса | `grep(pattern, module)` |
| **`find` вернул пусто, а объект наверняка есть** | `grep(pattern)` — промах поиска не равен отсутствию |
| Что перехвачено расширениями? | `overrides(object)` или `overrides(extension)` |
| Что делает вот это расширение? | `overrides(extension)` |
| Из чего состоит индекс, какие колонки? | `schema()` / `schema(table)` |
| Вопрос, которого нет в таблице | `sql(query)` — **после** `schema()` |
| Ответ «не найдено» выглядит подозрительно | `coverage()` |
| **Написал код модуля и собираюсь записать его в файл** | `check_bsl(source)` — ДО записи, структура + имена |

## Порядок работы

0. **`project`** — если сервер обслуживает несколько конфигураций, он
   откажет без этого параметра и перечислит доступные. Не угадывайте имя:
   `list_projects()` называет их. Ответ про ЧУЖУЮ конфигурацию выглядит
   правдоподобно, и это худший род ошибки — потому выбора по умолчанию нет.
1. **`find`** — от имени или от смысла. Возвращает адреса, не тела.
2. **`object`** / **`callers`** / **`movements`** — содержательный вопрос
   по найденному адресу.
3. **`read`** — только когда нужно именно тело процедуры. Не раньше:
   индекс отвечает на большинство вопросов без чтения кода.

`sql` — не первый ход, а последний: сперва посмотрите, нет ли готового
инструмента, потом спросите `schema`, и только затем пишите запрос.

Перед правкой кода или метаданных проверьте тему через `standards_1c`:
`view=search` находит исходный пункт ИТС, `view=article` показывает
контекст статьи, `view=clause` читает длинный пункт по частям. Затем
вызовите `project_practices` для принятых проектных правил и исключений.
Корпус ИТС общий для проектов; частное требование заказчика действует
только после приёмки и выше конфликтующего общего стандарта.

## Пишете код — проверьте до записи

`check_bsl(source)` за ОДИН вызов проверяет две вещи: структуру текста
и имена по индексу конфигурации. Звать НЕ после отказа платформы, а до
записи в файл: ошибка, найденная здесь, стоит одного вызова, найденная
в базе — цикла загрузки, отказа и разбора чужого сообщения.

| Что ловит | Пример |
|---|---|
| структура | незакрытый `КонецЕсли`, лишняя скобка, `Если` без `Тогда` |
| имя метода | вызван метод, которого в модуле конфигурации нет |
| число аргументов | передано шесть при четырёх объявленных |

Имена сверяются **не во всех** вызовах, и это намеренно: только
`Модуль.Метод`, где `Модуль` — объект этой конфигурации. Встроенные
функции платформы (`НСтр`, `ЗначениеЗаполнено`) и обращения через
переменные (`Объект.Записать`) пропускаются — индекс о них не знает, и
«не найдено» про них было бы ложью. Сколько проверено и сколько
пропущено — сказано в самом ответе, читайте эти числа.

**Инструменту нужен индекс.** Без него он не отвечает половиной правды,
а отказывает: разработка по конфигурации без индекса не ведётся вовсе.

## Пишете код — сначала возьмите подсказки

`assist_bsl(task, module, source)` нужен ДО и ВО ВРЕМЯ написания. Одним
вызовом он подбирает реальные методы и объекты конфигурации, короткие
места употребления, дополнения в позиции курсора и официальный синтаксис
из локального `shcntx_ru.hbk`. Пустой `source` даёт каркас, непустой
заодно проходит `check_bsl`.

Копировать можно только строки с `use=callable`. `reference_only` —
пример для чтения: внешний вызов из него не доказан. Если ответ говорит
`no_reliable_suggestions=true`, подсказки не выдумывать — уточнить задачу.
Слабые совпадения помощник скрывает намеренно: пустота честнее мусора.

## Права на утверждение

Сила вывода привязана к проделанной работе, а не к уверенности.

- **Разведка.** Один-два вызова, беглый поиск. Результат **провизорный**.
  Запрещено утверждать: «такого объекта нет», «это единственное место»,
  «метод нигде не используется», «правка ни на что не влияет».
- **Проверка** (по умолчанию). Целевые вызовы, обе стороны графа там, где
  это существенно, цитата из `read` под каждое утверждение о поведении кода,
  просмотрены все страницы выдачи, а не первая.
- **Аудит.** Полная проверка в объявленных границах, `coverage()` вызван,
  расхождения названы поимённо, **и перечислено то, что осталось невыясненным**.
  Аудит без раздела «чего я не проверил» — это проверка, назвавшаяся аудитом.

## Отсутствие ≠ полнота

Пустой ответ инструмента и факт об отсутствии в конфигурации — **разные вещи**,
и внешне они неотличимы.

Перед тем как написать «не найдено», «нет ни одного», «нигде не вызывается»:

1. вызовите `coverage()`;
2. прочитайте долю разрешённых рёбер: на БП это **34,0%** — то есть две трети
   рёбер графа ни на что конкретно не указывают, и вывод «никто не вызывает»
   по такому графу недопустим;
3. помните, что **чистый `coverage` означает отсутствие зафиксированного
   пробела, а не доказательство полноты**.

Три случая из нашей практики, где пустой ответ был принят за факт: молчание
по объектам в плоском XML читалось как «реквизитов нет»; поиск по неверному
узлу грамматики дал бы «расширения ничего не перехватывают» при живых
тринадцати; неверное имя XML-тега дало пустую колонку в заполненной таблице.

## Грабли

1. **`find` по подстроке и по смыслу — разные шкалы, и они не смешиваются.**
   Выдача раздельная (`objects`/`methods`/`modules` против `semantic`).
   Оценка семантики — косинус, её нельзя сравнивать с точным совпадением.
2. **Точный поиск может дать ноль там, где смысл даёт ответ.** На запрос
   «остатки товаров на складе» поиск методов вернул 0, семантика —
   `ЗаполнитьПоОстаткамНаСкладе` (1,00). Ноль от точного поиска не повод
   останавливаться.
3. **`read` требует однозначности.** Если метод есть в нескольких модулях,
   инструмент вернёт список кандидатов, а не тело: уточните `module`.
4. **`callers` с `depth` больше 2 растёт быстро.** Начинайте с 1–2 и
   расширяйте, а не наоборот.
5. **`sql` разрешает только `SELECT`/`WITH`, один оператор.** `PRAGMA`,
   `ATTACH` и табличные функции `pragma_*` отклоняются: устройство индекса
   спрашивают инструментом `schema`.
6. **Усечённая выдача говорит об этом сама** (`truncated: true`). Если поле
   стоит — вы видите часть, и вывод «всего N» неверен.
7. **Строки ответа позиционные: имена полей — в `columns`, по порядку.**
   `{"columns": ["name", "kind", "path"], "rows": [["А", "method", "…"]]}` —
   значение берётся по номеру колонки из `columns` того же ответа, а не по
   памяти о прошлом вызове: у разных инструментов порядок разный, и `r[3]`
   из `find` — не то же, что `r[3]` из `callers`. Схему таблицы ради этого не
   переспрашивать — `columns` уже в ответе. Хвостовые пустые значения не
   печатаются: строка бывает короче `columns`.
8. **«Не найдено» — это `found: false`, а не пустой список.** `object` и
   `callers` на отсутствующее отвечают `found: false` с подсказкой: `similar`
   (похожие имена), `places` (где метод с таким именем есть), `categories`
   (в каких категориях есть имя). Пустой раздел СУЩЕСТВУЮЩЕГО объекта назван
   в `empty_parts`. `movements` ищет точное имя (`substring: true` — подстрокой)
   и на пусто тоже ставит `found: false`. Столбец `via` объясняет, как
   получено совпадение: у `callers` — от какого из одноимённых методов, у
   подписок карточки — напрямую, через определяемый тип или на весь вид.

## Профили

Роли выдаётся не весь набор:

| Профиль | Инструменты |
|---|---|
| `all` | все инструменты, включая `sql` |
| `analysis` | без `sql` |
| `scout` | `list_projects`, `kb_1c`, `project_practices`, `standards_1c`, `find`, `object`, `assist_bsl`, `read`, `schema`, `coverage`, `grep`, `check_bsl` |

Если инструмента нет в `tools/list` — он не выдан этой роли, и обходить это
через `sql` не нужно: его в таком профиле тоже нет.

## Чего сервер не делает

- **не отдаёт файлы**: `read` возвращает одну процедуру по адресу из индекса;
- **не знает данных информационной базы** — только код и метаданные выгрузки;
- **не объясняет, при каких настройках механизм типовой работает** — это
  вопрос к справке конфигурации, а не к индексу кода;
- не доказывает бизнес-корректность предложенного метода: `assist_bsl`
  подбирает факты и строгие кандидаты, окончательное решение остаётся за разработчиком.
