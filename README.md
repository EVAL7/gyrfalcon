**Индексирует конфигурацию 1С целиком и отвечает на структурные вопросы за
миллисекунды.** Самая тяжёлая из проверенных — 1С:ERP Управление холдингом,
98 117 файлов и 752 335 методов — собирается за 2–2,5 минуты; ответ на вопрос
о графе вызовов приходит быстрее, чем агент успел бы открыть первый файл.

Разбор через [tree-sitter](https://tree-sitter.github.io/tree-sitter/) даёт AST
всех модулей, из него строится граф вызовов с классом разрешения на каждом ребре;
метаданные хранятся в индексе: реквизиты с типами и квалификаторами, движения регистров,
подписки, права ролей, перехваты расширений с адресом. Шестнадцать инструментов
MCP, три харнесса из коробки. Ни рантайма, ни облачного сервиса, ни ключа API.

> **Что он делает с вашим кодом.** Читает выгрузку конфигурации и пишет один
> файл индекса. При установке правит конфигурацию вашего агента — это его работа,
> и `--plan` показывает, что именно будет изменено, ничего не меняя. Никаких
> сетевых обращений: ни при сборке, ни при ответе, ни в фоне. Код не покидает
> машину, потому что серверу некуда его отправлять — он не умеет.

## Скорость

Разбор тысяч модулей — задача, где параллелизм даёт не проценты, а порядок:
свой поток на ядро, парсер `thread_local`, конвейер «воркеры → канал →
один писатель» (SQLite пишет в один поток).

**Замер на самой тяжёлой конфигурации** — 1С:ERP Управление холдингом,
98 117 XML-файлов, 29 818 модулей, 752 335 методов, 5 640 838 рёбер графа:

| этап | время |
|---|---|
| обход каталога | 10,0–10,5 с |
| разбор BSL | 25,1–25,5 с |
| разрешение имён | 10,4–13,9 с |
| метаданные | 18,5–27,7 с |
| построение индексов | 48,4–60,1 с |
| семантика | 7,1–8,5 с |
| **полная сборка** | **132–160 с** |

Диапазон, а не одно число: три прогона 29.08.2026 дали 132,5 / 154,5 /
159,8 с — разброс 20% при неизменном коде. Даёт его дисковый кэш, и
почти весь он приходится на построение индексов (48,4 → 60,1 с). Одно
наблюдение отсюда выглядело бы точнее, чем оно есть, — поэтому здесь
границы.

Индекс — 3,8 ГБ, ошибок разбора 0,09%. Разрешено 95,2% рёбер внутри
разрешимого: «не сумели разрешить» отличимо от «разрешать нечего».

## Быстрый старт

**Скачать готовый бинарь** — [релизы](https://github.com/aleksandrgradoboev-svg/gyrfalcon/releases/latest).
Один файл, больше ничего не нужно: ни Rust, ни Python, ни Docker, ни ключа API.

```bash
# собрать индекс по выгрузке конфигурации
gyrfalcon build <путь к src> --out config.db

# поднять MCP-сервер (stdio; по сети — --http, см. «Транспорт»)
gyrfalcon serve --db config.db

# прописать себя агенту (Claude Code / Kilo / Codex)
gyrfalcon install
```

`install` находит харнесс и прописывает сервер — подробности и что именно
кладётся в [«Работа с агентами»](#работа-с-агентами).

<details>
<summary>Сборка из исходников</summary>

```bash
git clone https://github.com/aleksandrgradoboev-svg/gyrfalcon
cd gyrfalcon
cargo build --release
# бинарь: target/release/gyrfalcon
```

Нужен свежий стабильный Rust (проект собирается на `stable`). Грамматики BSL и SDBL лежат в `vendor/` и собираются
своим `build.rs` — внешних зависимостей на сборку нет.
</details>

## Возможности

- **Полный индекс за минуты, а не часы** — 132–160 с на 29 818 модулях,
  параллельно по ядрам, свой парсер на поток.
- **Граф вызовов с классом разрешения** — у каждого ребра `confidence` и
  причина: «не сумели разрешить» отличимо от «разрешать нечего». 95,2%
  разрешено внутри разрешимого.
- **Перехваты расширений с адресом обеих сторон** — что подменяют
  (модуль + строка оригинала) и где лежит перехватчик.
- **Метаданные в индексе**, включая объекты, выгруженные плоским XML без
  каталога-спутника, — их пропускают инструменты, полагающиеся на структуру
  каталогов.
- **Поиск одним списком** — семь сигналов в одном балле, с объяснением,
  чем строка попала в выдачу.
- **Инструмент про собственную неполноту** (`coverage`) — сервер умеет
  сказать, чего он НЕ знает.
- **Полнотекстовый добор** там, где структурный поиск промахнулся: GUID,
  текст сообщения, кусок запроса.
- **Три харнесса из коробки** — Claude Code, Kilo, Codex. `install` находит
  установленное и прописывает сервер, скилл, три роли и хуки-подсказки;
  `--plan` показывает, что будет сделано, ничего не меняя.
- **Индекс — один файл SQLite**, самодостаточный и переносимый.
- **Пользовательская справка проекта** (`kb_1c`) — HTML из `Ext/Help`
  того же подключённого корпуса хранится в его индексе. Чужие проекты и
  прежняя общая KB-1С в поиск не подмешиваются.

### Встроенная справка Ext/Help

`gyrfalcon build <исходники> --out <индекс>/<project>.db` автоматически
извлекает страницы `*/Ext/Help/*.html` и сохраняет только нормализованный
UTF-8 текст, относительный путь, объект и версию из `Configuration.xml`.
Изображения, вложения, скрипты и CSS не сохраняются. Страницы короче 40
символов считаются заглушками и учитываются отдельно в отчёте сборки.
Повторные `build` и `kb refresh` читают и хэшируют HTML для проверки
изменений, но не разбирают неизменённые страницы. `kb refresh` также не
переписывает их записи в SQLite; полный `build` пересоздаёт файл индекса
и переносит в него прежние записи справки. Удалённые страницы убираются
из индекса; неполадки справки не блокируют сборку кода.
Автоматического слежения за `Ext/Help` нет: для обновления нужен очередной
`build` или явный `kb refresh`. Старый общий файл
`agents-data/_shared/kb/1c-help.db` для нового инструмента не требуется.

Каждый индекс — один проект. Запрос `kb_1c` обязательно задаёт одно имя
`project` из `list_projects`; отсутствие имени, `*` и массив не выбирают
глобальную базу. Ответ содержит версию, относительный адрес страницы и
идентификатор источника. Повторы текста объединяются в выдаче, но адреса
всех найденных страниц сохраняются в `alternate_sources`.

```text
kb_1c(project="bp-index", query="как оформить поступление денежных документов")
```

`kb_1c` отвечает по пользовательской справке конкретной конфигурации.
Синтаксис встроенных функций и методов платформы для написания BSL остаётся
в `assist_bsl.platform_api` и берётся из `shcntx_ru.hbk`.

```bash
gyrfalcon kb audit --src <исходники>                 # только счётчики, без записи
gyrfalcon kb audit --src <исходники> --out <новый.db> # QA-снимок, не рабочая KB
gyrfalcon kb refresh --db <старый индекс>            # дополнить индекс справкой из его source_path
gyrfalcon kb sync --db <индекс> --source-id addon --src <дополнительные исходники>
gyrfalcon kb remove --db <индекс> --source-id addon
```

Основной источник `primary` управляется `build`. Дополнительный источник
привязан к стабильному `source-id` и каноническому пути: повторный `sync`
добавляет/меняет/удаляет только его страницы одной транзакцией. При полной
пересборке существующие доступные дополнительные источники перечитываются;
недоступные больше не включаются. Для намеренного отключения используйте
`kb remove`; удаление проектного индекса удаляет и всю его справку.

## Работа с агентами

```bash
gyrfalcon install              # все найденные харнессы
gyrfalcon install --plan       # что будет сделано, ничего не меняя
gyrfalcon install --harness claude
```

Установщик кладёт четыре вещи: конфигурацию MCP, скилл, три роли и
хуки-подсказки. Ничего экспериментального не включает, чужих настроек
не переписывает, режимов «разрешить всё» не трогает.

| Харнесс | Конфигурация MCP | Что ещё кладётся |
|---|---|---|
| **Claude Code** | `~/.claude.json` | скилл `~/.claude/skills/gyrfalcon/`, три роли в `~/.claude/agents/`, хуки в `~/.claude/hooks/` |
| **Kilo** | `.kilo/mcp.json` | скилл `.kilo/skills/gyrfalcon/`, три роли в `.kilo/agent/`, плагины в `.kilo/plugins/` |
| **Codex** | `$CODEX_HOME/config.toml` | скилл, роли и хуки в том же корне (`~/.codex` по умолчанию) |

### Транспорт: stdio по умолчанию, HTTP по флагу

```bash
gyrfalcon serve --db config.db                     # stdio: клиент запускает процесс сам
gyrfalcon serve --db config.db --http              # http://127.0.0.1:8788/mcp
gyrfalcon serve --db config.db --http --port 9000
gyrfalcon serve --index-dir data --profile all --auto-update --http --port 8788 --bind 127.0.0.1
```

Stdio требует, чтобы клиент **запускал бинарь сам**: в конфигурации агента
лежит путь и аргументы; `install` прописывает этот вариант. HTTP позволяет
держать один постоянно работающий сервис для нескольких клиентов, в том
числе локального Codex. Адрес `127.0.0.1` доступен только на этой машине.

Для Claude Code пропишите адрес командой:

```bash
claude mcp add --transport http gyrfalcon http://127.0.0.1:8788/mcp
```

Или задайте его в `.mcp.json` проекта:

```json
{
  "mcpServers": {
    "gyrfalcon": { "type": "http", "url": "http://127.0.0.1:8788/mcp" }
  }
}
```

Для Codex добавьте в пользовательский `~/.codex/config.toml` или
проектный `.codex/config.toml` (у доверенного проекта):

```toml
[mcp_servers.gyrfalcon]
url = "http://127.0.0.1:8788/mcp"
```

Если проектный файл уже содержит `[mcp_servers.gyrfalcon]` с `command` и
`args`, замените их на `url`: проектная настройка перекрывает пользовательскую.
Новый сеанс Codex читает обновлённый адрес при запуске.

**Это Streamable HTTP, а не HTTP+SSE.** Транспорт с двумя адресами
(`GET /sse` и `POST /message`) введён ревизией протокола 2024-11-05 и помечен
устаревшим уже в 2025-03-26 — его заменил Streamable HTTP: один адрес, ответ
телом обычного POST. Клиенты, умеющие SSE, умеют и то, что пришло ему на
смену; реализовывать отменённое сервер не будет (Р-019).

Что транспорт делает и чего не делает:

| | |
|---|---|
| адрес | один: `POST /mcp` (на `/` отвечает тоже — описка в конфиге частая) |
| `GET /mcp` | **405**. Потока событий нет: сервер не шлёт сообщений по своей воле — ни списка инструментов, ни прогресса, ни вопросов клиенту |
| сессии | **не заводятся.** Состояние процесса общее и по клиентам не делится (Р-007), а `Mcp-Session-Id` обещал бы изоляцию, которой нет |
| `Origin` | проверяется: чужой — 403. Без этого локальный сервер читается чужой страницей руками браузера |
| привязка | `127.0.0.1`, пока не сказано иное. Переставляется `--bind` — см. «В контейнере» |
| параллельность | пул из `--workers` потоков, умолчание 4. Вызовы по одному проекту идут одновременно; досборка индекса ждёт идущие вызовы и не пускает новые, пока пишет |
| тело запроса | до 1 МиБ; больше — 413. Вызов инструмента столько не весит |

Аутентификации, ограничения запросов и TLS нет — ни того, ни другого, ни
третьего сервер не изображает. Через недоверенную сеть его пускают туннелем,
а не публикацией порта.

### В контейнере

```bash
docker build -t gyrfalcon .
```

**Собрать индекс** — выгрузка внутрь только на чтение, индекс наружу:

```bash
docker run --rm \
  -v /путь/к/выгрузке:/src:ro \
  -v /путь/к/индексам:/data \
  --user "$(id -u):$(id -g)" \
  gyrfalcon build /src --out /data/config.db
```

**Отвечать по stdio** — клиент запускает контейнер сам, как запускал бы
бинарь. Так это прописывается агенту:

```json
{
  "mcpServers": {
    "gyrfalcon": {
      "command": "docker",
      "args": ["run", "-i", "--rm",
               "-v", "/путь/к/индексам:/data:ro",
               "gyrfalcon", "serve", "--db", "/data/config.db"]
    }
  }
}
```

**Отвечать по HTTP** — и вот здесь нужен `--bind`:

```bash
docker run --rm -p 127.0.0.1:8788:8788 \
  -v /путь/к/индексам:/data:ro \
  gyrfalcon serve --db /data/config.db --http --bind 0.0.0.0
```

`127.0.0.1` внутри контейнера — **его собственная петля**, и снаружи по ней
не достучаться даже через опубликованный порт. Поэтому умолчание там
бесполезно, а `--bind 0.0.0.0` открывает порт сети контейнера — не машине
целиком: наружу его выносит `-p`, и в примере он выведен на петлю **хоста**.
Сервер о переставленном интерфейсе предупреждает при старте, а не молчит.

Аутентификации и TLS у него по-прежнему нет. Кто открыл порт — тот и
отвечает за то, что перед ним стоит (Р-019).

**Словарь семантики лежит внутри образа** — `/usr/share/gyrfalcon/dictionary.db`,
монтировать его не надо:

```bash
docker run --rm -v /путь/к/выгрузке:/src:ro -v /путь/к/индексам:/data \
  --user "$(id -u):$(id -g)" gyrfalcon \
  build /src --out /data/config.db --dict /usr/share/gyrfalcon/dictionary.db
```

40 МБ к образу — цена того, что сборка работает из коробки. Без `--dict`
индекс соберётся, но `find` останется без семантического сигнала, и заметить
это можно только по качеству ответов.

Образ читает и не пишет: работает от пользователя `10001`, индекс
монтируется `:ro`. Собранный на хосте индекс должен быть ему читаем —
отсюда `--user` в примере со сборкой.

**Через compose** — то же самое, но без длинных командных строк:

```bash
docker compose up -d --build     # MCP по HTTP на 127.0.0.1:8788
docker compose logs -f           # что сказал сервер при старте
docker compose --profile build run --rm build   # собрать индекс
```

Пути и порт задаются переменными окружения или файлом `.env` рядом:

| переменная | смысл | умолчание |
|---|---|---|
| `INDEX_DIR` | каталог с индексами `*.db` — каждый файл отдельный проект | `./index` |
| `SRC_DIR` | выгрузка конфигурации для профиля `build` | `./src-1c` |
| `BIND_HOST` | на каком адресе **хоста** открыть порт | `127.0.0.1` |
| `PORT` | порт хоста | `8788` |
| `HOST_UID` / `HOST_GID` | от кого собирать индекс, чтобы файл не лёг с чужим владельцем | `10001` |

Сборка отдельным профилем намеренно: это разовая работа, а не служба, и по
`up` она подниматься не должна. Каталоги умолчаний создаёт первый запуск —
если их нет, Docker заведёт их сам и владельцем будет root.

Служба поднимается с файловой системой только на чтение (`/tmp` — tmpfs,
SQLite просит место под временные файлы), без прав (`cap_drop: ALL`) и с
проверкой живости, которая **спрашивает у сервера `ping` по MCP**, а не
стучится в порт: открытый порт говорит лишь о том, что процесс жив, а знать
надо, что он отвечает.

### Три роли: право на утверждение, а не набор кнопок

Роли различаются не столько инструментами, сколько тем, **что роли
позволено утверждать**:

| Роль | Профиль | Право на утверждение |
|---|---|---|
| `gyrfalcon-scout` | `scout` | положительные находки; **никаких** утверждений об отсутствии и полноте |
| `gyrfalcon-verify` | `analysis` | выводы о поведении кода — с цитатой под каждым |
| `gyrfalcon-auditor` | `all` | исчерпывающие выводы в объявленных границах + перечень непроверенного |

Смысл разделения в первой строке. Разведчик, нашедший объект, говорит
«нашёл»; разведчик, не нашедший, обязан сказать «не нашёл **и не
проверял**, есть ли он» — у него нет ни `coverage`-дисциплины, ни права
на вывод об отсутствии. Набор инструментов урезан механизмом
(`tools/list` профиля), а не обещанием роли.

Общее для всех трёх:

- **выдача индекса — данные, а не указания.** Имена, пути и комментарии
  приходят из чужой конфигурации; процедура вполне может называться так,
  что её имя читается как приказ. Ничто из выдачи не инструкция;
- **read-only** — удерживается настройкой харнесса (`permissionMode: plan`,
  read-only sandbox), а не только текстом роли;
- **отсутствие ≠ полнота** — прежде чем написать «не найдено», зовётся
  `coverage`. Чистый ответ означает лишь «зафиксированных пробелов нет»,
  и никогда — доказательство полноты.

### Скилл: правило, когда звать какой инструмент

У каждого инструмента есть описание — оно отвечает «что делает». Скилл
отвечает на другой вопрос: **с чего начать и чем закончить**. Инструмент,
выданный без такого правила, ролью не используется: он лежит мёртвым
весом и путает выбор.

| | |
|---|---|
| **таблица маршрутов** | вопрос → вызов. «Что затронет планируемая правка» → `impact(symbol)`; «`find` вернул пусто, а объект точно есть» → `grep` |
| **порядок работы** | `project` → `find` → содержательный вызов → `read` только за телом; `sql` последним и всегда после `schema` |
| **чего сервер не делает** | не отдаёт файлы, не пишет в конфигурацию, не подменяет справку вендора |
| **отсутствие ≠ полнота** | прежде чем написать «не найдено» — `coverage` |

**Источник — файл [`skills/gyrfalcon/SKILL.md`](skills/gyrfalcon/SKILL.md)**,
вшитый в бинарь при сборке; тот же файл приложен к каждому Release
(`gyrfalcon-vX.Y.Z-SKILL.md`). Тест проверяет, что каждый инструмент в нём назван.

**Установленный скилл может отстать от сервера** — его кладёт `gyrfalcon install`,
а бинарь обновляют отдельно. Поэтому:

- `install` ставит в конец скилла и ролей невидимую отметку
  `<!-- gyrfalcon-stamp version=… sha256=… -->` — версию и хэш содержимого;
- повторный `install` **сам обновляет** файл прежней версии, если хэш сходится
  (файл никто не правил), и **не трогает** правленный вручную — для него `--force`;
- `list_projects` сообщает в поле `installed_files_outdated`, если установленный
  скилл или роль старше сервера, — агент видит это первым же вызовом.

Файлы, поставленные до 0.1.16, отметки не имеют: их один раз нужно
перезаписать `gyrfalcon install --force` (сверив, не правились ли они).

### Хуки: подсказка, а не запрет

Три события, и все три **никогда не блокируют вызов** — только добавляют
контекст:

| Событие | Что делает |
|---|---|
| старт сессии | напоминает, что индекс есть, и говорит о его свежести |
| старт субагента | то же самое для дочерней роли |
| перед `Grep`/`Glob` | подсказывает, что тот же вопрос дешевле задать индексу |

Хук, который отказывает, ломает работу агента при первой же своей ошибке.
Хук, который подсказывает, в худшем случае бесполезен.

## Инструменты MCP

Шестнадцать широких инструментов вместо россыпи мелких: агенту нужен ответ,
а не конструктор из хелперов. Каждый отдаёт таблицу с колонками, каждый
называет усечение вслух.

| Инструмент | Отвечает на вопрос |
|---|---|
| `kb_1c` | Как работать в выбранной конфигурации по её встроенной пользовательской справке `Ext/Help`? Требует `project` |
| `find` | Есть ли такой объект, метод, модуль? Ищет по имени, по подстроке и **по смыслу**, ранжирует одним баллом из семи сигналов |
| `object` | Карточка объекта: реквизиты с типами и квалификаторами, табличные части, синонимы, предопределённые, формы, движения, права, опции, подписки и задания |
| [`assist_bsl`](#помощник-написания-bsl) | Помочь написать BSL: реальные методы и объекты конфигурации, официальный синтаксис платформы, короткие примеры, дополнения и каркас |
| `callers` | Кто вызывает метод и кого вызывает он — транзитивно, на заданную глубину, с классом разрешения на каждом ребре |
| `impact` | Последствия планируемой правки до diff: вызывающие, платформенные входы, формы, права и адресные метаданные |
| `read` | Тело одной процедуры по адресу из индекса. Не файл и не модуль |
| `project_practices` | Общий базис стандартов 1С и принятые правила выбранного проекта; локальные кандидаты выдаются отдельно |
| `standards_1c` | Поиск по общему корпусу стандартов 1С и принятым правилам; корпус статей собирается локально |
| `overrides` | Перехваты расширений **с адресом обеих сторон**: что подменено и где лежит подменяющий код |
| `movements` | Движения документов по регистрам — из объявленных метаданных, а не только из кода |
| [`detect_changes`](#что-сломает-эта-правка) | Что сломает эта правка: git diff → задетые методы → радиус поражения с оценкой риска |
| `grep` | Полнотекстовый добор по телам модулей: GUID, текст сообщения, кусок запроса |
| `schema` | Устройство индекса: таблицы, колонки, число строк. Спрашивать **перед** `sql` |
| `coverage` | **Чего в индексе НЕТ**: файлы с ошибкой разбора, нерешённые рёбра, доля разрешённого |
| `sql` | Read-only SQL к индексу — для вопросов, которых нет в наборе выше |
| [`check_bsl`](#проверка-кода-перед-записью) | Проверить модуль BSL до записи: синтаксис, существование вызываемых методов и число аргументов, неопределённые переменные, вызовы, недоступные на клиенте |
| [`list_projects`](#несколько-конфигураций-в-одном-сервере) | Какие конфигурации обслуживает сервер, и проверено ли, что индексы свежи |
| [`delete_project`](#удаление-индекса) | Удалить индекс конфигурации: закрыть, снять слежение, убрать файл. Только профиль `all` |

Порядок в таблице — от частого к редкому, он же порядок в `tools/list`.
Два последних — про сам сервер, а не про конфигурацию.

### Стандарты 1С и практики проекта

`project_practices(project)` всегда выдаёт общий базис из 1200 принятых,
нормализованных правил 1С. Базис встроен один раз и не копируется в проекты.
Дополнительно инструмент читает `.gyrfalcon/project-practices.json` рядом с
исходниками выбранного индекса: типовой код и доработки входят в проектный
профиль на равных. Частые паттерны сами по себе инструкциями не считаются.

При первом обращении пустой профиль создаётся автоматически. Быстрый проход
по BSL-модулям собирает кандидатов; повторно заполненный профиль без команды
не перезаписывается. Кандидатов можно посмотреть через `view=candidates`,
а принять после проверки — командой `practices accept`. Пары областей служат
свидетельствами к общему правилу, а не размножают его в десятки карточек.
Полный поиск последовательностей вызовов и AST-фрагментов пока исследовательский:
результаты быстрого прохода не следует принимать без содержательной проверки.

`standards_1c(view=practices)` читает встроенный базис. Для поиска по полным
статьям `view=search` нужен локальный корпус `shared-v8std.sqlite`, который
собирается инструментами `tools/v8std-*.py` из официального справочника.
Тексты статей и локальная база в репозиторий не включены.

Есть два способа наполнить профиль:

```text
gyrfalcon practices import --src <исходники> --project <индекс> --commit <sha> --document <практики.md>
gyrfalcon practices add --src <исходники> --project <индекс> --commit <sha> --rule <правило.json>
```

Импорт документации создаёт кандидаты с адресом раздела; ручная команда
добавляет правило с источником `manual`. Оба источника проходят одинаковую
проверку перед выдачей как принятых проектных правил:

- `status: "verified"`, `legacy: false`;
- выборка не меньше 10 и измеренная точность не ниже 0,90;
- `source_commit` совпадает с коммитом индекса;
- каждый адрес доказательства (`module`, `method`) существует в этом индексе.

Пустой или устаревший профиль не добавляет проектных правил; общий базис
остаётся доступным. Типовой код и исторические исключения слишком легко
выглядят как «обычная практика». Формат проектного профиля версии 1:

```json
{
  "version": 1,
  "project": "my-index",
  "source_commit": "<git commit from index_meta>",
  "rules": [{
    "id": "server-validation",
    "title": "Проверять данные на сервере",
    "guidance": "Новая команда вызывает серверную проверку до записи.",
    "status": "verified",
    "legacy": false,
    "source": {"kind": "documentation", "path": "docs/practices.md", "anchor": "line:12"},
    "sample": 12,
    "matches": 12,
    "evidence": [{"module": "CommonModules/Example/Ext/Module.bsl", "method": "ПроверитьПередЗаписью"}]
  }]
}
```

### Порядок, в котором их зовут

Не произвольный: каждый следующий опирается на адрес, полученный предыдущим.

```
find ──→ read        нашли метод, читаем его тело
     ──→ object      нашли объект, смотрим карточку целиком
     ──→ callers     нашли метод, разворачиваем граф влияния

grep                 когда find вернул пусто, а объект наверняка есть
schema ──→ sql       сначала фактическая схема, потом запрос по ней
coverage             когда «не найдено» выглядит подозрительно
```

Три правила, вытекающие из этого порядка:

1. **`read` не читает файл** — только тело одного метода по адресу из
   индекса. Модули наружу не уходят вовсе;
2. **`sql` без `schema`** — запрос по памяти о схеме, а не по схеме;
3. **пустой ответ проверяется `coverage`** — «не найдено» и «не
   проиндексировано» неотличимы, пока не спросишь.

### Схемы параметров сервер отдаёт сам

Полные схемы — типы, умолчания, обязательность — приходят в `tools/list`
при подключении. Дублировать их здесь значило бы завести второй источник
правды, который разойдётся с первым молча: в документе всё ещё написано
«по умолчанию 20», а в коде уже 50.

Каждый инструмент несёт описание, объясняющее не только что он делает,
но и **когда его звать** — это же правило вшито в скилл (ниже).

### Профили: инструмент, которого роли не нужен, у неё отсутствует

| Профиль | Инструменты | Кому |
|---|---|---|
| `scout` | `find`, `object`, `read`, `schema`, `coverage`, `grep` | разведка: найти и посмотреть |
| `analysis` | `scout` + `callers`, `impact`, `overrides`, `movements` | разбор: граф, последствия правки, расширения, движения |
| `all` | `analysis` + `sql` | аудит: произвольный запрос к схеме |

Профиль задаётся при установке (`--profile`) и режет `tools/list`, а не
прячет кнопку. Причина: инструмент, лежащий мёртвым весом без правила,
когда его звать, — это шум в выборе, а не запасная возможность.

### Поиск: один список, семь сигналов

`find` не отдаёт отдельные разделы «точные совпадения» и «по смыслу» — он
считает **один взвешенный балл** и объясняет, чем строка попала в список:

```
0.950 [имя      ] method  ПолучитьКонтрагента
0.416 [имя      ] method  ПолучитьКонтрагентаИКонтактноеЛицоПоСтрокеАдреса
0.196 [смысл    ] method  ПолучитьДанныеКонтрагента
```

Сигналы: точность имени, **синоним объекта** (русское название из
метаданных — «адресная книга» находит `АдреснаяКнига`), BM25, семантическая
близость, редкость слов, использование в коде, связность по графу.
Каждый нормируется по выдаче перед сложением.

### Что сломает эта правка

`detect_changes` отвечает на вопрос ревьюера одним вызовом вместо обхода
вызывающих руками: берёт `git diff`, находит в изменённых файлах методы
и обходит от них граф вызовов.

```
detect_changes()                                  → против main
detect_changes(since="HEAD~3", depth=3)           → против коммита
detect_changes(base_branch="main", direction="both")
```

Изменения берутся из **трёх источников сразу**: закоммиченное против базы
(`<base>...HEAD`, от точки расхождения — чужие правки, приехавшие в базу
после ветвления, не попадают), незакоммиченное в рабочем дереве и новые
файлы. Третий источник существует потому, что `git diff` не видит
неотслеживаемое: без него новый модуль не появился бы в выдаче вовсе.

Риск — расстояние в графе, а не составная оценка: hop 1 → `CRITICAL`,
2 → `HIGH`, 3 → `MEDIUM`, дальше `LOW`. Смешивать сюда ширину радиуса,
`confidence` рёбер и экспортность заманчиво и неверно: сумма разнородных
сигналов выглядит точным числом, не будучи им, а расстояние — измеримый
факт графа.

Сводка `by_risk` и `total` считаются **по всему радиусу**, список строк
режется `limit`. Разделение намеренное: перечень нужен обозримый, счёт
обязан быть верным — иначе предел, сработавший на первом хопе, показал бы
«CRITICAL: 30» там, где задето 143 метода.

`has_overrides` предупреждает о том, чего в diff не видно: если изменённый
метод перехвачен расширением через `&Вместо`, в боевой базе исполнится не
то, что показывает правка.

### Помощник написания BSL

`assist_bsl` вызывается до и во время генерации кода. Он собирает за один
вызов то, что слабая модель редко связывает сама цепочкой из пяти инструментов:

```
assist_bsl(task="заполнить заказ клиента", module=".../ObjectModule.bsl")
assist_bsl(task="...", module="...", source="...", cursor=127)
```

- методы, объекты и реквизиты из индекса конфигурации;
- короткие реальные места вызова найденных методов;
- точный синтаксис платформенного API из локального `shcntx_ru.hbk`;
- дополнения в позиции курсора;
- безопасный каркас для пустого черновика;
- `check_bsl` для непустого черновика.

Выдача отсекается строго. Конфигурационный кандидат проходит при лексическом
совпадении не короче четырёх знаков либо при достаточной сырой семантической
близости; нормированный балл не используется — лучший из мусора всегда получил
бы единицу. Платформенная страница проходит при точном имени либо совпадении
минимум по двум значимым основам слов. Если надёжного нет, ответ содержит
`no_reliable_suggestions=true`, а не список случайных соседей.

Поле `use=callable` означает, что форма вызова подтверждена контекстом модуля
или экспортным методом общего модуля. `reference_only` — материал для чтения,
копировать его как внешний вызов нельзя.

Источник платформы ищется по `GYRFALCON_PLATFORM_BIN`, затем среди локальных
установок 1С; выбирается самая новая числовая версия. HTML справки наружу не
отдаётся: сервер один раз строит компактный каталог методов, свойств,
конструкторов и событий и сохраняет его в постоянный кэш
(`GYRFALCON_CACHE_DIR` меняет каталог). Ключ включает канонический путь,
версию, размер, время изменения и SHA-256 исходного HBK: обновление платформы
автоматически строит новый кэш, а неизменная справка больше не разбирается.

### Проверка кода перед записью

Инструмент для того, кто **пишет** код, а не только читает его. Зовётся до
записи файла: ошибка, найденная здесь, стоит одного вызова, найденная при
загрузке в базу — цикла «загрузка → отказ → разбор сообщения платформы → правка».

```
check_bsl(source)                    синтаксис, имена, переменные, контекст — один вызов
check_bsl(source, module="Documents/Заказ/Forms/ФормаДокумента/Ext/Form/Module.bsl")
                                     то же, реквизиты формы — точно по модулю
check_bsl(source, deep=true)         плюс прозрачные метрики сложности
```

Проверок внутри две, и они разной природы: структуру видит разбор текста,
имена — только индекс конфигурации. Разделить их на два инструмента было бы
честнее по устройству и **хуже по делу**: слабая модель не зовёт и один
разведочный инструмент, а два не позовёт тем более. Замер по языку запросов
показал это числом — `query_check` был назван в одной методике из сорока,
и модель его не звала.

| Что ловит | Пример |
|---|---|
| структура | незакрытый `КонецЕсли`, лишняя скобка, `Если` без `Тогда` |
| имя метода | вызван метод, которого в модуле конфигурации нет |
| число аргументов | передано шесть при четырёх объявленных |
| неопределённая переменная | голое имя, которое не объявлено в методе и модуле, не известно платформе и не является реквизитом — с позицией, как у конфигуратора |
| недоступное на клиенте | в `&НаКлиенте`: `Новый Запрос`, `ТекущаяДатаСеанса()`, `Справочники`, метод серверного общего модуля без флага «Вызов сервера» |

Переменные и контекст сверяются по трём источникам: дереву разбора, справке
установленной платформы (`shcntx_ru.hbk`, раздел «Доступность») и индексу
(реквизиты, предопределённые, значения перечислений, флаги общих модулей).
Без справки эта часть не делается и называется в `not_checked`. Код под
`#Если` на контекст не проверяется. Калибровка на трёх типовых конфигурациях
(22,8 млн голых имён) — ноль ложных замечаний; подробности — `docs/decisions.md`, Р-023.

Структурный слой — tree-sitter, форк грамматики `kvant`. Замер 27–28.08.2026
на корпусе 12 257 модулей: **0,00% файлов с ошибкой разбора**. Пропуск `;`
ошибкой не считается, и это по делу: в BSL операторы разделяет перевод строки.

**Имена сверяются не во всех вызовах, и это главное решение в инструменте.**
Замер по 187 234 вызовам заведомо правильного кода конфигурации:

| что сверяем с индексом | ложных тревог |
|---|---|
| все имена подряд | **47,5%** |
| только `Модуль.Метод`, где `Модуль` — объект конфигурации | 1,14% |
| + локальные имена модуля (переменные, параметры, счётчики) | 0,50% |
| + предопределённые элементы | **0,26%** |

Причина первой строки видна в хвосте частот: `НСтр`, `ЗначениеЗаполнено`,
`ТипЗнч` — встроенные функции платформы; `Вставить`, `Найти`, `Следующий` —
методы её типов. Ни того, ни другого в индексе **конфигурации** нет и быть не
может. Инструмент, врущий в половине случаев, хуже отсутствующего: его
перестают читать вместе с той половиной, где он прав.

Поэтому голый вызов здесь не «не найден», а **«не проверялся»**, и рядом с
вердиктом всегда стоит, сколько вызовов проверено и сколько пропущено. Итог на
полном корпусе — 6750 модулей, 131 744 проверенных вызова, **0,26%** замечаний,
69 модулей в секунду.

**Без индекса инструмент не работает** — не «отдаёт половину проверки», а
отказывает, как и остальные: разработка по конфигурации 1С без индекса не
ведётся вовсе, а половинный зелёный ответ читается как полный.

## Несколько конфигураций в одном сервере

Один сервер обслуживает столько конфигураций, сколько индексов лежит
в каталоге. Разные конфигурации собираются параллельно и независимо —
каждая в свой файл.

```bash
gyrfalcon serve --index-dir C:/индексы      # все *.db в каталоге — проекты
gyrfalcon serve --db config.db              # один индекс
```

**Реестра нет.** Проект — это имя файла: `C:/индексы/erpuh.db` → проект
`erpuh`. Добавить конфигурацию значит собрать её индекс в этот каталог,
убрать — удалить файл. Отдельный реестр умеет расходиться с диском
(запись есть, файла нет), а каталог такой болезни не имеет: он и есть
источник правды.

| Инструмент | Что делает |
|---|---|
| `list_projects` | Какие конфигурации знает сервер, и **проверено ли, что индекс свеж** |
| `delete_project` | Удалить индекс конфигурации: закрыть, снять слежение, убрать файл |

Параметр `project` есть у **каждого** инструмента и принимает три формы:

```
project: "erpuh"                  одна конфигурация
project: ["erpuh", "bp"]          несколько сразу
project: "*"                      все, какие есть
```

### Молчаливого выбора нет

Сервер с несколькими конфигурациями **отказывает** без `project`, а не
берёт первую попавшуюся:

```
ОТКАЗ: не указан параметр project. Сервер обслуживает несколько
конфигураций, и молча выбрать одну нельзя: ответ про чужую конфигурацию
выглядит правдоподобно. Доступны: bp, do, erpuh
```

Это тот же довод, что у `coverage` и у стоп-условий контура: ответ про
не ту базу не выглядит ошибкой. Он выглядит ответом.

Два отказа различаются намеренно — забытый параметр и неизвестное имя
требуют разного действия:

| Случай | Ответ |
|---|---|
| `project` не передан | «не указан параметр project» + перечень |
| `project: "zup"`, а его нет | «проект 'zup' не найден. Это утверждение о **реестре сервера**, а не о конфигурации 1С» + перечень |

Вторая формулировка не педантизм: «не найдено» от сервера навигации по
1С читается как «нет такого объекта в конфигурации». Здесь же речь о том,
что сервер про такую базу не знает вовсе.

### Как узнать, что всё в порядке

Свежий индекс в ответах инструментов **молчит** — так дешевле по токенам.
Но молчание двусмысленно: оно значит и «расхождений нет», и «проверка не
работает, а ты не знаешь». Поэтому его можно спросить прямо:

```json
list_projects → "freshness": {
  "checked": "исходники сверены, расхождений нет",
  "changed_files": 0,
  "watching": true,
  "watch_note": "правки в исходниках видны сразу: подписка на события ФС"
}
```

Четыре разных состояния, и ни одно не прячется за молчанием:

| `checked` | Что значит |
|---|---|
| `исходники сверены, расхождений нет` | всё в порядке, и это проверено |
| `идёт первый обход` | ответ ещё не гарантирован |
| `индекс отстал` | есть изменённые файлы, число в `changed_files` |
| `не выполнена` | каталог исходников недоступен, причина в `reason` |
| `не открывался в этой сессии` | сторожа нет, потому что проект не спрашивали |

**`watching: false` — отдельная беда.** Она значит, что подписка на
события файловой системы не встала: расхождения, возникшие ПОСЛЕ старта
сервера, замечены не будут. Без этого поля такой сервер молчал бы точно
так же, как исправный.

### Удаление индекса

```
delete_project(project: "erpuh")
```

Казалось бы, лишний инструмент: проект — это файл, удаление — это `rm`.
Проба показала обратное: **пока сервер работает, `rm` не проходит вовсе**
(`WinError 32`, файл занят процессом). Пришлось бы гасить сервер, роняя
работу всех агентов ради одной базы.

Инструмент делает то, чего `rm` не умеет: закрывает соединение, снимает
сторожа свежести, удаляет файл со спутниками SQLite и называет исход
словом — `deleted` / `not_found` / `delete_failed` с причиной.

Доступен только профилю `all`: это единственная разрушающая операция
сервера, и роль, чьё дело читать, стирать индексы не должна. Удаляется
**индекс**, а не исходники конфигурации.

### Ответ по нескольким не склеивается

```json
{
  "by_project": {
    "bp":    {"found": 2, "rows": [["ДобавитьПОД_Документ_ЗаказКлиента_Отправка", …]]},
    "do":    {"found": 0, "rows": []},
    "erpuh": {"found": 2, "rows": [["ЗаказКлиента", …]]}
  },
  "projects_queried": 3,
  "projects_answered": 3
}
```

Строки разных конфигураций одинаковы на вид и означают разное:
`Контрагенты` из ЕРП.УХ и `Контрагенты` из БП — разные объекты разных баз.
Склеенная таблица это скрывает, и вывод о «дубле» или «единственном
совпадении» делается по перемешанным данным.

Отказ по одному проекту не отменяет остальные — он приходит как ошибка
своей строки, а `projects_answered` показывает, сколько ответило на самом
деле. Потолок — 32 проекта за вызов: каждый это открытие индекса и полный
проход по нему.

## Свежесть индекса

Индекс отстаёт от исходников молча: он отвечает уверенно и неверно.
Поэтому сервер следит за этим сам.

**Обход один раз при старте, дальше подписка на события файловой
системы.** Устройство выбрано замером, а не вкусом: полный обход
ЕРП.УХ стоит 9,88 с против 0,12 с на сам ответ, и повторять его на
каждый вызов значило бы сделать сервер в 80 раз медленнее там, где
он и ценен.

Что видит агент:

| Состояние | Что в ответе |
|---|---|
| свежий | **ничего** — платить токенами за «всё хорошо» в каждом ответе не за что |
| отстал | `stale`: сколько файлов изменено, примеры путей, возраст индекса |
| первый обход ещё идёт | «свежесть ещё проверяется» — незнание не выдаётся за свежесть |

Отставание считается двумя признаками сразу: `mtime` файлов против
времени сборки **и** git-коммит рабочей копии против записанного при
сборке. Каждый по отдельности слеп: первый не видит `git checkout`
(содержимое вернулось, время правки новое), второй — правки, не дошедшей
до коммита, а разработчик живёт именно в ней.

### Догонять самому: `--auto-update`

По умолчанию сервер только предупреждает. С флагом он ещё и догоняет —
инкрементом по изменившимся `.bsl`, перед ответом на вопрос агента:

```bash
gyrfalcon serve --index-dir <каталог> --auto-update
```

Выключено по умолчанию намеренно: сборка трогает файл, которым сервер
отвечает, и включать её за человека нельзя. (Так же устроено у образца,
где `auto_index` умолчанием `false` — вопреки их же README.)

Три правила, каждое со своим доводом:

- **правка метаданных отменяет досборку целиком.** Инкремент не принимает
  `.xml`, а дособрать одни модули и промолчать про метаданные значило бы
  оставить индекс расходящимся ровно там, где никто не проверит. Остаётся
  отметка «индекс отстал» — она и говорит, что нужна полная сборка;
- **успех — единственное основание забыть правку.** Упавшая или пропущенная
  досборка оставляет файл в очереди: иначе отказ выглядел бы как «изменений
  не было», и расхождение стало бы невидимым;
- **не чаще, чем раз в интервал** — 5 с плюс 1 с на каждые 500 файлов,
  потолок 60 с. На ЗУП это 29 с: правка догоняется на первом вызове после
  паузы, а не на каждом вопросе подряд.

Полная сборка не запускается никогда и ни при каких настройках: она стоит
минуты, и решение о ней принимает человек.

`list_projects` показывает состояние раздельно — `changed_before_start`
(накопилось до запуска сервера, автодосборка это не трогает) и
`changed_while_running` (появилось при живом сервере, это она догоняет).

### Догнать вручную

```bash
gyrfalcon update --db config.db              # найти изменившиеся .bsl и учесть
gyrfalcon update --db config.db <файлы…>     # переиндексировать названные
```

| Корпус | Полная сборка | Инкремент |
|---|---|---|
| 1С:Документооборот (22 829 файлов) | 16,0 с | **6,0 с** |
| 1С:ERP УХ (127 935 файлов) | 132,5 с | **10,1 с** |

Чего инкремент **не** делает — и говорит об этом сам, а не только здесь:

- **не пересчитывает семантику** (IDF считается по всему корпусу): новый
  метод войдёт в поиск по смыслу после следующей полной сборки;
- **не перерешает рёбра, ведущие В изменённый модуль.** Вызовы к новому
  экспортному методу из других модулей остаются в классе `unknown`.
  Их число печатается как `stale_edges` — цена названа числом;
- **не принимает `.xml`.** Правка метаданных задевает таблицы
  перекрёстными ссылками, и выборочная чистка дала бы тихо расходящийся
  индекс. Такая правка требует полной сборки, и команда отвечает отказом,
  а не молча пропускает файл.

## Модель данных индекса

Что `sql` видит и какими ключами это адресуется. Раздел нужен ровно
затем, чтобы запрос писался по фактической модели, а не по догадке
о ней, — та же причина, по которой `schema` зовётся перед `sql`.

### Классы разрешения рёбер

Главная ось графа. У каждого ребра `calls` — класс и `confidence`:

| Класс | Что значит | Разрешимо |
|---|---|---|
| `local` | вызов метода того же модуля | да |
| `common_module` | `ОбщийМодуль.Метод` | да |
| `object_manager` | `Справочники.Х.Метод` — менеджерский модуль | да |
| `platform_var` | вызов через переменную; нужен вывод типов | **нет** |
| `platform_global` | функция платформы (`НСтр`, `СокрЛП`) | **нет** |
| `unknown` | **не сумели разрешить, хотя могли бы** | да |

Различие между `unknown` и двумя `platform_*` — не педантизм, а
знаменатель. Доля разрешённого считается **внутри разрешимых классов**
(`is_resolvable`), иначе её задаёт не качество резолвера, а состав
корпуса: конфигурация с обилием вызовов платформы «улучшала» бы метрику
сама собой. Отсюда две разные цифры в `coverage`: 95,2% внутри
разрешимого и 33,4% по всем рёбрам — вторая ничего не говорит о нас.

`unknown` — это признание, а не мусорная корзина. Слить его с
`platform_global` значило бы спрятать свой недочёт за свойством языка.

### Адресация метода: `callee_key`

```
<путь модуля>::<имя метода в нижнем регистре>
CommonModules/РаботаСФайлами/Ext/Module.bsl::получитьфайл
```

Регистр снят намеренно: 1С регистронезависима в именах, и `ПолучитьФайл`
с `получитьФайл` — один метод. Ключ пуст (`NULL`) ровно тогда, когда
ребро неразрешимо: `callee_key IS NOT NULL` и есть признак разрешённости,
по которому считается доля.

### Что разрешено в `sql`

Только чтение. **Три рубежа, а не один:**

1. **соединение открыто с `SQLITE_OPEN_READ_ONLY`** — единственный рубеж,
   который держит сама SQLite, а не разбор текста;
2. **разбор запроса**: ровно один оператор, начинается с `SELECT` или
   `WITH`. Поимённо запрещены `INSERT`, `UPDATE`, `DELETE`, `DROP`,
   `CREATE`, `ALTER`, `REPLACE`, `ATTACH`, `DETACH`, `PRAGMA`, `VACUUM`,
   `REINDEX`, `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`;
3. **лимит строк** — 200 по умолчанию, 2000 жёстким потолком, чтобы
   ответ не вынес контекст агента.

`ATTACH` и `PRAGMA` названы отдельно не для полноты списка: первый цепляет
чужой файл — в том числе на запись, — второй меняет поведение соединения.
Оба проходят проверку «это же не `INSERT`» и потому перечислены поимённо.

Порядок рубежей важен: главный — первый. Проверка текста вспомогательная,
она даёт понятный отказ вместо ошибки SQLite, но полагаться на неё одну
нельзя — обойти разбор текста всегда проще, чем права соединения.

**Отвергнутый запрос отвечает отказом с причиной, а не пустой выдачей.**
Это то же правило, что у `coverage` и у всего сервера: пустой ответ
неотличим от факта о конфигурации, и молчаливый отказ превратился бы
в «в конфигурации такого нет».

## Чего сервер не делает

- **не содержит LLM** — это структурный бэкенд, интеллект остаётся у агента;
- **не ходит в сеть** ни при сборке, ни при ответе;
- **не пишет** в конфигурацию: индекс и SQL строго read-only;
- **не гарантирует полноту молчанием** — на это есть `coverage`. Ответ
  «не найдено» может значить «не проиндексировано», и сервер даёт это
  проверить, а не делает вид, что перечислил всё;
- **не подменяет справку**: как механизм 1С устроен, видно по коду; при
  каких настройках он работает — вопрос к документации вендора.

## Если не работает

| Признак | Причина и что делать |
|---|---|
| агент не видит сервер в `/mcp` | путь к бинарю в конфиге не абсолютный. Проверить: `gyrfalcon install --plan` покажет, что и куда прописано |
| «индекс … недоступен» на любом вызове | индекс не собран или путь в `--db` неверен. Собрать: `gyrfalcon build <путь> --out config.db` |
| `find` не находит объект, который точно есть | сначала `coverage` — возможно, модуль не разобрался. Затем `grep`: структурный поиск промахивается на том, чего нет в именах |
| ответ помечен `stale` | индекс отстал от исходников. `gyrfalcon update --db config.db` |
| «свежесть индекса не проверена» | каталог исходников недоступен: индекс собран на другой машине или выгрузка переехала |
| `sql` отвечает «запрос отклонён» | разрешены только `SELECT`/`WITH`, один оператор. Причина названа в самом отказе |
| нет `sql`, `callers` или `overrides` в списке | профиль режет набор. Смотреть, каким `--profile` поставлен сервер |
| `grep` работает минуту | сузить `module` — на 30 тыс. модулей это разница между секундой и минутой |
| «объект не найден» после правки метаданных | инкремент `.xml` не берёт. Нужна полная сборка |
| по HTTP приходит `404` | адрес без `/mcp`: сервер отвечает на `POST /mcp`, а не на любой путь |
| по HTTP приходит `403` | `Origin` не localhost. Сервер обслуживает только свою машину — снаружи его пускают туннелем |
| `--port без --http` | порт слушает только транспорт HTTP; stdio его не открывает |
| в контейнере HTTP не отвечает снаружи | нужен `--bind 0.0.0.0`: петля контейнера снаружи недостижима даже при `-p` |
| в контейнере «индекс … недоступен» | каталог не смонтирован или не читается пользователем `10001`. Проверить: `docker run --rm -v …:/data:ro gyrfalcon list-… ` либо запустить с `--user "$(id -u):$(id -g)"` |

## Переменные окружения

| Переменная | Смысл |
|---|---|
| `GYRFALCON_DB` | Путь к индексу, о котором знают хуки-подсказки |

Одна, и это не упущение. Хуки не ищут индекс сами: путь задаёт тот, кто
ставил сервер. Угадывание дало бы подсказку про **чужой** индекс — хуже,
чем отсутствие подсказки.

Остальное задаётся флагами команды (`--db`, `--profile`, `--port`,
`--threads`), а не окружением: флаг виден в конфигурации агента, который
его запускает, а переменная — нет.

## Визуализация

```bash
gyrfalcon ui --db config.db    # localhost:8787
```

Солнечная диаграмма подсистем, граф движений документов по регистрам,
перехваты расширений с адресами.

## Устройство

```
crates/
  gyrfalcon-parser/   разбор BSL и XML-выгрузки: tree-sitter, метаданные, формы
  gyrfalcon-index/    индекс SQLite: метаданные, граф вызовов, семантика, ранжирование
  gyrfalcon-mcp/      бинарь gyrfalcon: MCP-сервер, установщик, визуализация
docs/                 решения об устройстве сервера с доводами
Dockerfile            образ: сборка индекса и оба транспорта
```

Индекс — один файл SQLite, самодостаточный. Тела модулей в нём не хранятся:
это раздуло бы его кратно, а `grep` читает файлы по перечню из индекса.
